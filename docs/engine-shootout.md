# Bonsai Halo M1 engine shootout

[Operating manual](../README.md) · [shared contract](../../data/engine-shootout/CONTRACT.md) · [runner](../tools/shootout_runner.py)

The M1 weight image is `../../data/bonsai2/PTQ1_0.gguf`. `--profile max` chooses the installed wide-deployed exact prefill/serving route and Q4 DFlash2 exact-output target verification for singleton decode; `--plain` measures undecorated target decode. In independent-stream `--batch` it chooses mode 19 (A4 FFN, A4-both sequence input/output, INT8 GDN state and four-step deferred updates), with a 256-token default context. The latter is an **approximate map**, not the exact route. An explicit `HALO_GDN_STATE` or `HALO_GDN_DEFER` overrides the preset. A larger context must be set explicitly. The packed state-region stride is not selected by max because its mixed commit/replay/rollback acceptance is red; 128-slot runs enable it explicitly and label it experimental.

Run `python3 tools/shootout_runner.py ALL` on a quiet host, or one of S1–S5/Q1–Q2. It writes a `receipt.json` plus stdout/stderr for each point under `../../data/engine-shootout/receipts/bonsai-halo/M1/<scenario>/<UTC time>/`. `../../data/engine-shootout/runners/bonsai-halo/run.py` points at the installed runner. `--only` selects exploratory points. All GPU processes, including the short PPL control, use `tools/run-batch-compare`; that admission pauses and restores the resident server. The runner records binary/library digests, revision, dirty tree, host load and clock verdict. For S5 the child server is started *inside* the GPU reservation and terminated before its scope ends. A low-clock or peer-loaded receipt is preliminary, not a headline quiet-host panel.

S1 uses 128 and 4096 exact token-ID prompts, 256 requested completions. S2 compares serial and Q4 DFlash2 with token-ID digests; a speculative rate is exact-output only if those digests and produced counts match. S3 uses 512 and 4096 token-ID prompts. S4 uses distinct 128-token IDs per independent slot and records actual emitted tokens, since EOG can shorten a completion. S5 measures streaming HTTP completion tokens and median first nonempty SSE delta, at 1/8/32 clients. The server applies its chat template to these raw prompt bytes, so S5 is a separate served endpoint rather than a replay of the raw offline IDs.

`tools/perplexity --ppl FILE --chunks N --route deployed|wide-deployed|wide-a4 [--logits-out FILE|--reference FILE]` is a real-model teacher-forcing path. It tokenizes with the GGUF's libllama vocabulary, prepends BOS if the model requests it, discards the incomplete last chunk, resets state at each 512-token window, replaces each window's first token with BOS if required, and scores **255** positions (logits at 256..510 against target tokens 257..511). This is the *actual* `llama-perplexity -c 512` loop, not a nominal 256-scored-token convention. Full float32 reference distributions are row-major; `--reference` computes exact→route KL and top-1 agreement over the same scored rows, and fails on count mismatch. Use `--chunks 0` for the full test: this corpus has 297,193 model tokens and **580** complete windows. `--start-chunk N` resumes a partition without restarting from the beginning; the tool checks an appended reference file's exact row count before writing. A timed-out segment whose output holds complete windows can be resumed at `file_size / (255 * 248320 * 4)`, and its last `chunk N/580` line gives its running cumulative perplexity. Aggregate disjoint segments by scored-token-weighted NLL, not by averaging perplexities. Q1/Q2 receipts for different chunk counts must never be compared. The paired reference file is retained by count under the M1 receipt root.

The initial two-chunk cross-check: Halo exact FP32/deployed PPL **8.745971898** over 510 predictions; llama.cpp HIP on the same PTQ1_0, `-c 512 -b 512 -ub 512 --chunks 2`, PPL **8.7357** (0.12% difference). Halo's first chunk is 6.386280 against llama.cpp 6.3888. This is close but not bit-identical numerical evaluation. The approximate mode19 A4 FFN + INT8 state/defer4 route gave PPL **8.955072224**, KL(exact||route) **0.030857300 nats**, top-1 **0.935294118** over the same 510 predictions. These were taken under concurrent CPU load, which affects rates but not these fixed-input scores. The separate wide-deployed f32 route gives PPL **8.768256105**, KL **0.008782509**, top-1 **0.974509804** against deployed exact; wide-A4 with f32 state gives PPL **9.012937417**, KL **0.031313579**, top-1 **0.925490196** on the same two chunks. A full-file exact reference began September 24 and completed its first 324/580 chunks before its 1100-second scope limit, cumulative PPL **8.868008** at that boundary. Its reference file holds precisely 324 complete windows and must be resumed from chunk 324. Full-test quality and the remaining route controls are pending the sequential sweep.

## Candidate custody and boundaries

The installed tree already contains the accepted ordered target K-parts, DFlash2 Q4, wide deployed prompt and serving routes, A4 FFN, shape-selected head/sequence row widths, INT8 state and deferred writes. These are composed in the preset above, rather than cherry-picked from experiments without acceptance. Clone studies remain in their owned checkouts: `bonsai-proj-wide` documents five losing projection delivery experiments; `bonsai-gdn-traffic` has unresolved merges and no accepted complete-model result; `bonsai-gdn-state` attempts another storage refactor while its mixed acceptance fails; `bonsai-ffn-map`, `bonsai-pass-schedule` and `bonsai-prefill-sched` are unfinished candidate measurements. No unaccepted dirty change is silently installed. [State-region stride](state-region-stride.md) measured 616.5 tokens/s at 64 streams and 615.4 at 128 under its own short-context boundaries, but mixed acceptance fails on its base with either stride. The proposed 128-slot contract point is therefore an *experimental result*, not a headline exact or accepted max rate.
