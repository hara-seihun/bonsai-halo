# Qwen 31+1 split is not invariant to batch-row order, even under gathered GDN

The rejected broad direct GDN cache writer changed the swapped row's old R1 history. Is the gathered path a row-order-invariant oracle for the same *logical sequence* transition? A matched four-arm, full-vocabulary/serialized-state experiment answers **no** on the pinned Qwen3.6-35B-A3B Q4_K_M runtime. This is a separate observation from the direct writer's local failure.

## Matched transition and result

The probe seeds 32 distinct eight-token sequences, runs one stable generated 32-row step, and then supplies the **same next greedy token, position 9 and logical sequence ID** to each sequence in the third step. In the `swap` arms only, the *batch row order* of sequences 0 and 1 is exchanged; tokens follow their sequence IDs (unlike the earlier swapped-ID probe, which intentionally did not remap token values). Each of 32 complete 248,320-float heads is saved by **logical sequence ID**, not by batch row. The third step's swap induces the native 31+1 split, while normal order remains one 32-row call. The two GDN arms are selected runtime default and `GGML_CUDA_GDN_FUSED_ROWS=0`, with unchanged GGUF, source artifact, precision, attention and requested heads.

| Comparison (third step) | Different logical heads | Logit words differing | Complete serialized state |
| --- | --- | --- | --- |
| normal default vs normal gathered | none, all three steps | 0 | **bit-identical**, including metadata, KV and 30 R/S layers |
| swap default vs swap gathered | ID 1 only | **248,320/248,320** | R/S row 1 first differs at recurrent layer 1; layer 0 and all KV agree |
| normal gathered vs swap gathered | IDs **0, 1 and 4** | **248,317; 248,320; 248,317** | same final recurrent metadata (physical row i owns sequence i), but R0 physical row 0 differs in 8,079/24,576 FP32 words; S0 row 0 differs in 508,482/524,288; subsequent layers spread to rows 0, 1 and 4. KV tensors associated with sequence stores 0, 1 and 4 also differ. |

All prior-step complete heads match by logical ID (all 15,892,480 float words in steps 0 and 1). All 32 third-step argmax IDs agree between the two gathered runs; that does **not** make the 744,954 changed full-head floats or changed state bit-identical. The row-4 effect is present with *both* gathered arms and the selected guard; it is **not caused by the rejected direct writer**. Likewise, the rejected direct writer's additional row-1 state/logit change remains even after conditioning on the swapped batch order. The selected stable-32 direct writer exactly reproduces gathered heads and the entire state on normal order. The source and instrument do not locate the first divergent forward op in the reordered gathered graph or establish language-quality harm; they identify two independent numerical-map questions that previous one-control-vs-candidate acceptance conflated.

The finite contract is the saved three-step input and four installed-artifact executions, observed as bitwise FP32 heads and serialized state. This is not a mathematical impossibility of permutation-invariant MoE/GDN scheduling, nor a speed measurement. A difference between two row schedules can result from native graph lifetime, routing/group reductions or recurrence state handling; byte comparisons alone do not assign causality. The row-4 KV/state divergence is a concrete reason to instrument the *gathered* 31+1 graph first instead of ascribing all swap variation to the GDN direct writer. The native selected guard, model and service default remain unchanged.

## Reproduction and next experiment

`tools/qwen-moe/gdn_permutation_equiv.cpp` saves the four full-head and whole-state observations. `tools/qwen-moe/gdn_permutation_equiv.py` checks all logical heads, serialized regions, physical recurrent rows and file hashes. [The receipt](../../data/qwen-moe/gdn-permutation-equiv/receipt.json) binds the installed GGUF, source, probe, four raw heads, four complete 2,114,206,957-byte states and wrapper logs. The source is compiled with the selected packaged `libllama`; each arm runs under `tools/run-batch-compare --runtime-max 42s --memory-gib 43 --host-reserve-gib 7 --exec`. `normal`/`swap` choose the third-step row order; `GGML_CUDA_GDN_FUSED_ROWS=0` chooses gathered. The four wrapper logs show service restoration. The GPU lock is free and `bonsai-halo.service` active after the panel.

**Next:** capture the source row indexes and old convolution operands for physical rows 0, 1 and 4 at R0/R1, *plus the attention KV write indices* across the gathered 31+1 segment seam in an unchanged no-callback graph. Establish row-order equivalence (or deliberately choose a documented order-dependent numerical map) for the gathered control before judging a reordered direct writer against it. A subsequent direct-writer repair still needs exact full heads and complete state on both normal and reordered schedules; the current guarded stable-32 deployment is accepted and should not be broadened on the strength of a single-row local check.
