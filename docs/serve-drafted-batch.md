# Concurrent speculative serving at four slots

The four-slot server loses DFlash2 speculation when requests share a decode step. A prototype verified independent draft chains in one replayable mode-4 target pass. Its four-client HTTP throughput was worse than plain batching, and one two-client completion changed when the two-client control repeat did not. That is not an exactness pass. The prototype is preserved in commit `70c8e4e` and the raw panels below, but its serving switch and scheduler are not in the current source. The default and installed service still run the prior shared plain-decode route.

The investigation did find a separate defect in `forward_batch`. Mode 4 launches one layer at a time. The persistent kernel resets its local feature-capture index on each launch, so its prior capture path only wrote the first of five DFlash2 features. `forward_batch` now copies the residual stream at each of the five layer boundaries for mode 4, as its wide route already does. This is a repair to the existing batch inference contract, not a change to the served decode choice.

## Capture and replay check

`tools/serve_capture_check` runs the ordinary eight-row target and mode 4 on independent state slots with the same eight input tokens, then rolls back both to the first three rows and runs the same four-token continuation. It zeroes the shared feature buffer before every pass so stale captures cannot masquerade as writes. At each pass it checks the row argmax, five captured feature planes against the ordinary target with a 5% relative RMS tolerance, finite values, and rollback bookkeeping. No drafter weights are needed. Build with `make tools/serve_capture_check` and run it under `tools/run-batch-compare --exec ./tools/serve_capture_check`. The positive panel is `capture-check.log` in the raw directory below. The five initial feature RMS values are 0.421, 0.904, 1.144, 1.462 and 3.619; differences from the ordinary target are 0.0026, 0.0083, 0.0110, 0.0136 and 0.0412. After rollback, the five differences are 0.0025, 0.0083, 0.0130, 0.0154 and 0.0489. Every compared argmax agrees.

As a regression control, restoring the predecessor's mode-4 capture conditions, rebuilding the tool and running the same check fails at feature 1: reference RMS 0.904, difference RMS 0.904. Feature 0 still agrees to RMS 0.002, which isolates the missing four later planes. That control is `capture-regression-negative.log`; the source was restored immediately. This check establishes feature placement and the exercised replay bookkeeping, not byte identity of all model state. The residual differences can arise from the model's atomic K-split reduction, so its 5% tolerance is a regression threshold, not a proof that mode 4 and the single-target path have identical numerical maps at every position.

## Unaccepted serving prototype

The final prototype panel used one executable, SHA-256 `dde6bd03b7a65d2daed14384f160f8c66bba06cfdf88db2285ca58e364b28bcb`, full 32768-token context and 64 completion tokens per request. Its two-client result was 59.6 to 81.8 aggregate tok/s with 91/252 drafts accepted. At four clients it was 93.6 to 85.2 tok/s with 173/581 accepted. The clock sampler recorded 2887 MHz p50 and another 2.2 busy host cores. An earlier four-client panel was also negative, 87.7 to 77.8 tok/s.

The final cross-arm HTTP check found one divergent completion at **two** clients. The repeated default arm agreed at two clients and diverged once at four clients. A four-client repeat says nothing about the two-client mismatch. The prototype did not establish whether the two-client change was an atomic-reduction draw, a different target map, or a per-sequence replay defect. The capture check above does not resolve that question, nor does the acceptance count. Do not treat the +37% two-client measurement as a shipping gain until a matched two-client target-output and full logical-state comparison passes. A four-client route is a loss even if that work eventually clears it.

Raw JSON and per-request outputs: [`batch-comparison/serve-drafted-batch/`](../../../data/bonsai2/batch-comparison/serve-drafted-batch/), especially `final-ab.json`, `panel-01.json` and `panel-02.json` before the capture repair, `single-mode4.json`, `capture-fix.json`, and the two capture-check logs. `tools/serve_load.py --repeat-control` keeps each first-arm repeat in the JSON; it reports the served identity floor but does not excuse a divergence at a concurrency whose own repeat agrees.

One attempted additional HTTP panel failed before launch with `D-Bus connection terminated while waiting for jobs`. The user systemd manager remained PID 1283 and the wrapper's subsequent panels succeeded. Its scope and service events in the user journal show concurrent GPU owners entering their own scopes and restoring the service; no further bus reset appeared. The final resident service is active. Do not race a current GPU owner to restart it.
