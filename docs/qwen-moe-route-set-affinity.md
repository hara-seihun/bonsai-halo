# Static co-route pairs on real Qwen prompt routes

Could a fixed two-expert bank layout turn repeated co-routing into a cheap paired consumer? On each of forty layers I formed the exact maximum-weight matching of 256 expert IDs using the 113-token train prompt's eight selected IDs per token. A pair earns one hit when both IDs appear on a token. The matching uses blossom optimization on the 28 co-occurring pairs per token; unobserved IDs are paired in sorted order. The held panel is the separate 126-token prompt. This is a fixed layout selected before held routes, not a fresh pairing chosen for each token.

| Pair layout per layer | Hits on 5,040 held route rows | Fraction of 20,160 possible pair slots |
| --- | ---: | ---: |
| Uniformly shuffled IDs, fixed seed | 550 | 2.73% |
| Adjacent IDs ordered by train expert frequency | 1,561 | 7.74% |
| Train-optimal exact maximum-weight matching | 4,409 | 21.87% |
| Held-optimal hindsight matching | 10,729 | 53.22% |

Train-optimal pairing hits 9,778 of 18,080 possible train slots, or 54.08%, but only 21.87% of held slots. This is not just a difference between the two prompts: fit on the first half of the train prompt and score the second half, and the layout hits 2,112 of 9,120 slots against 5,436 hindsight. Fitting the first half of held and scoring its second half hits 2,822 of 10,080 against 6,041 hindsight. A fixed pairing learned from roughly sixty consecutive prompt rows does not capture the apparently strong in-sample pair affinity. Train and held share only 63 exact eight-ID route occurrences among 5,040 held layer-token rows; just 37 held rows repeat another held route in their own layer. These sets describe selected IDs, not equal activations or weights.

The exact finite matching optimum follows because the number of hits equals the sum of co-occurrence counts of the chosen disjoint edges. Maximum-weight matching optimizes that sum over all static pair partitions on the chosen capture. A held oracle is thus an upper bound for this fixed-pair grammar on these rows. Across uniformly random fixed pairings, each token has expected `28/255` complete pairs, or 553.4 expected hits on the held panel; the seeded control observed 550. The train-selected layout couples at most 8,818 of 40,320 held expert assignments, even granting a free pair consumer. It does **not** save an expert weight image: distinct experts retain distinct packed bytes, and the installed runtime already shares the gate/up input and groups expert assignments. One hit could remove at most one *hypothetical* per-expert control/preparation operation that a joint pair consumer otherwise repeats, before routing tests, occupancy, gather/scatter and pair-image placement. It establishes no latency gain, loss change, or even a worthwhile native kernel.

This is a negative for a fixed pair catalogue trained on this short prompt, not for online pairing or learned approximate expert codes. The high held oracle means pair fusion may still be worth examining with substantially broader disjoint training routes and a real per-pair native overhead measurement. An online pairing must choose IDs after routing, preserve each expert's dot and ordered FP32 weighted sum, and pay for irregular pair-image access. Exact whole-route caching is less attractive still on these captures: a layer-specific eight-expert set transfers on 1.25% of held rows.

`tools/qwen-moe/route_set_affinity.py` writes [the receipt](../../data/qwen-moe/all-layer-routes/route-set-affinity.json) with all 80 input hashes, capture provenance, source hash, per-layer matched pair IDs and counts. The route callback cuts the graph, so the observation contract is callback-cut prompt routing, not uninstrumented decode. This CPU analysis did not acquire the GPU or change the installed image, executable, model arithmetic or resident service. The next decisive question is whether a native pair consumer has any cost to remove beyond the already shared input and grouped dispatch; generated decode routes and longer disjoint prompt samples are needed before assigning a stable pair layout.
