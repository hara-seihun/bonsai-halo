# Target batch logits at the MTP near tie

The selected target runtime computes a different FP32 logit map when several causal tokens enter one `llama_decode` call. This alone can reverse the same token choice that separated plain generation from Q4 MTP on the September 23 list request. No draft model participates in this replay.

## A diagnostic callback changes the map

A two-token target-only replay of the first continuation row exposed a trap in locating the first divergent layer. Without graph callbacks, the width-two row differs from the singleton row at 248,319 of 248,320 logits, with maximum absolute difference .197883. The plain winner's margin is 2.098101. Adding callbacks that read layer outputs leaves those numbers unchanged, and the first different *captured* tensor is the routed MoE output in layer 1. That is not a noninvasive localization result.

Ask the backend evaluation callback to read `ffn_moe_probs` at every layer, keeping the same model, tokens, context, batch settings and both calls. Now the first width-two row and the singleton row agree at **every logit bit**. The width-two winner's logit remains 22.37257 in both arms; the singleton map changes, with winner margin 2.043587 instead of 2.098101. The captured routing probabilities, selected weighted inputs and routed output also agree between widths on layer 1. A callback at `ffn_moe_logits` alone leaves the original 248,319-bit difference; a callback at normalized routing weights removes it. Capturing only layer 1's probabilities makes that layer's routed output equal but leaves 248,320 final logits different. The distinction accumulates across layers.

This is a **graph-execution boundary experiment**, not a repair or a numerical proof about the uninstrumented first divergent operation. The scheduler's callback path splits each backend graph view at a requested tensor and synchronizes before reading it (`ggml-backend.cpp`, scheduler loop). Those boundaries can alter execution and its output; even observing a tensor is an intervention here. Do not select a kernel for repair using the layer-1 callback trace as if it observed the original graph. The next exact-engine question is which backend graph execution across the probability/weight boundary changes the singleton arithmetic, first on a one-layer reproducer, then on the uninstrumented full model. A future callback-based comparison must state its own map. Nothing here shows that the MTP 71st-token fork disappears, nor does a two-token logit agreement establish a whole-model speedup.

The diagnostic is `batch_logits.cpp --layer-probe` with `QWEN_PROBE_ROUTER=ffn_moe_probs` and optional `QWEN_PROBE_LAYER=1`. It compares one plain and one two-token target decode at the first continuation row, and prints per-layer FP32 bit counts. [The receipt and raw wrapper logs](../../data/qwen-moe/acceptance/batch-layer-probe/receipt.json) pin the installed source, executable, model, input and service restoration. Run the control without `--layer-probe`; run the probed arm with the environment above. Both use `tools/run-batch-compare --runtime-max 42s --memory-gib 30 --host-reserve-gib 4 --exec` before the diagnostic path. No serving default or installed executable changed.

`tools/qwen-moe/batch_logits.cpp` generates 96 greedy tokens one at a time from the exact server prompt, clears the model state, and replays those *same* token IDs through the same target and context. Each replay requests every row's full vocabulary logits. It compares one-token calls with two-, four- and eight-token calls, shifting the first call by 0–3 tokens to expose alignment. All rows use causal positions and sequence 0. The selected source is `b4c67ced9f6bac6b1661b25714946d999374e06f`; the model is the pinned `ac0e2c11…` GGUF. The 96 generated IDs equal all 96 IDs from the [plain server list receipt](../../data/qwen-moe/mtp/benchmarks/20260923T191754Z-plain-590c76ac/receipt.json). The [Q4 MTP receipt](../../data/qwen-moe/mtp/benchmarks/20260923T191817Z-mtp-abcf4b60/receipt.json) first differs at zero-based generated index 71.

At row 71, one-token target chooses ID 4980 over ID 33565 with FP32 logits 26.0549965 and 25.8452873. Width four with one initial singleton chooses ID **33565**, with logits 25.8716984 for 4980 and 26.0318146 for 33565. These are exactly the two IDs in the plain/MTP server fork. Width one reproduces every one of the 97 full-vocabulary rows bit-for-bit after clearing and replaying the same context, so state reset and tokenization are controlled. The first row of every arm, the prompt output, also agrees. From the first batched continuation row onward almost all vocabulary floats differ; the maximum absolute deviation over the measured rows ranges from 1.96 to 2.89 across the batched arms. This is not a roundoff bound for other prompts or a whole-model quality measurement.

The batched target's arithmetic is sufficient to produce the observed greedy fork on the *identical* plain prefix, without an indexing error or a divergent draft prefix. The replay does not show that MTP used this precise four-row alignment at that verification step; an indexing error remains possible. It does rule out treating multi-token target logits as a bit-identical oracle for plain one-token greedy generation. A verifier that promises the plain stream must recover its one-token target choice at uncertain near ties, with the candidate and its required state reconciled. [A no-cut allocation probe](qwen-moe-mtp-near-tie.md) now rejects the tempting direct-force of singleton fused top-k at multirow width: its row-0 output overlaps row-1 router logits in the selected graph. Nonoverlapping allocation, not a guard deletion, is the next same-map engine candidate. Test a selective one-token replay/rollback against the actual server fork before admitting MTP, and charge the replay frequency and complete generated-token rate. Simply accepting the batched argmax changes the requested numerical map.
