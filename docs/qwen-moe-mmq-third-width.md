# Third MMQ body on real Qwen routes: compute saved, staging unchanged

A third J=32 body between J=16 and J=64 reduces full-tile expert arithmetic positions on the held 126-token forty-layer prompt, but **does not reduce the activation staging column count** versus the already constructed J=16/64 plan. It also adds 39 gate/up dispatches and 2,968 row/column tiles. This is a checked static construction and a useful reason to lower and measure the two-body candidate *first*, not evidence for installing three bodies.

The [input- and source-hashed CPU receipt](../../data/qwen-moe/all-layer-routes/mmq-third-width.json) (SHA-256 `7b5f72d855df4466324cb839b0a775fa17574eb1ed8f32459746af26714596a1`) replays all forty pinned layer route arrays in each train/held split. `python3 tools/qwen-moe/mmq_third_width.py --output ../../data/qwen-moe/all-layer-routes/mmq-third-width.json` enumerates all native sets of at most three J widths and chooses the fewest padded positions per group, then passes and output tiles as ties. Each group is constrained to no more complete logical image passes than the installed global J=64 tile. This is free partition/dispatch; no native body is compiled or changed.

For held width 126 (the 128-row tile; the 256 cap sees the same rows), all positions and staging columns below refer to **gate/up** with 1,024 output rows; down doubles positions, blocks and staging. Image passes refer to grouped weight-image visits, *not* measured DRAM bytes.

The third body saves 12,156,928 positions, 10.7677% of the two-body count and 3.7050% of the installed count. It closes 77.77% of the **remaining padded-position gap** to the free eight-body minimum (12,156,928 of 15,630,336), but incurs another 39 launches and 2,968 row/column tiles (3.95% above two bodies). It changes 371 held expert groups from J64 to J32; group assignments, per-group K order and logical image passes remain unchanged. The independent 113-token train split also picks J16/32/64: 106,250,240 → 93,667,328 positions, 74,304 → 77,376 tiles, 80 → 118 launches, same 4,907 image passes and 1,390,848 staged columns. On 32-row tiles the optimal two-body plan already is J16/32; a third body makes no improvement. The JSON retains the 16/32/64/128/256 cap comparisons and source, model, capture, occupancy and native-source hashes.

**Why staging is exactly flat, not a lucky sample.** Native J16 and J32 have I=64 and 128 threads; J64 has I=128 and 256 threads. For output rows divisible by 128, replacing one J64 tile for an expert group of size 17–32 with one J32 tile halves issued output positions (`R × 64` to `R × 32`), but doubles row/column tiles (`R/128` to `R/64`). Each tile stages J activation columns, so the complete staged-column count stays `R/128 × 64 = R/64 × 32 = R/2`. J16 remains the choice at 1–16; J64 remains at 33–64. All captured 65–128 groups retain their J64 two-pass path under the no-extra-pass constraint. Output row widths 1,024 and 2,048 satisfy this identity. Logical expert weight bytes are not reduced by this per-output-row partition; the row segments are distinct.

This is not a native gain. Additional launch, grid, barrier, occupancy and activation-quantization costs are unpriced. A checked scheduling map can preserve each original tile's internal arithmetic, but an implementation must demonstrate finite FP32 logit/state identity and complete prompt/batched rates. The next decisive experiment remains **native two-body J16/64 compact scheduling against selected J64**, with installed full-model identity. Only if that survives should a three-body arm be tried: the third width has no staging-byte saving and strictly more dispatch/blocks, while its arithmetic reduction is bounded above by the counts here. Single-token MMVQ is unaffected.
