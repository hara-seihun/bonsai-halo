# A weight request moved inside the block does not recover the generation gap

At 32 streams, pinning the sequence projection's weight addresses to one cache block saves 7.08% of the whole step. That is a useful ablation of the exposed weight stream, not a proof of a time bound or a promise that software lookahead collects the same gain. I requested the next block's two code loads and scale after slice zero of the current block, leaving seven slices of expansion and matrix work before use. The 32-stream step instead went from 75.710 to 76.313 ms in a paired production-build comparison. The input projection grew from 8.980 to 10.805 ms. Nothing ships.

The exact source diff, binaries, raw traces, clock logs and build hashes are in [`seq-weight-cover/`](../../data/bonsai2/batch-comparison/seq-weight-cover). The origin is `6b72745`. `candidate.patch` is the complete arm; the final tree contains this report, not an unused kernel path.

## What was asked

The deployed four-bit sequence projection loads each 128-block's two code words and scale at the head of the block that consumes them. The candidate keeps the deployed lane addresses, weight image, token ownership, K order, `iu4` matrix operations and FP32 accumulation. It loads block zero ahead of the loop and, after the current block's first K16 slice, requests block `b+1`. The pending block becomes the next iteration's operand. This is deliberately different from the former `SEQ_OP_STREAM` arm, which coupled lookahead to the wave-uniform base and cost 22.39% at 32 rows. Here the default address form stays put and the request begins *after* slice zero rather than beside the current block's loads.

The source was first compiled with a named diagnostic arm and then as the production route, with no pin-control define and no runtime selector. The control was compiled from the same tree with `HALO_SEQ_WEIGHT_COVER=0`. Recompiling the untouched `6b72745` source produced exactly the control's `sequence_batch.o` and `batch_profile` SHA-256, `1cd56202...` and `ffb5d8a3...`. The production candidate binary is `e323f67f...`; see `candidate-hashes.txt` and `canonical-hashes.txt` for full hashes. The copied binaries are paired in one GPU-lock hold by `paired.sh`. `batch_profile` originally hashed the checkout's `tools/batch_profile` path, even for a copied executable. `metadata-reconciliation.json` preserves every original field and JSON hash and records the corrected identity from the verified binary manifests. The corrected JSON now names the executed copy in `binary_sha256` and its matching projection source hash in `executable_source_sha256`; `source_sha256_rollup` remains the workspace snapshot taken by the original process, not necessarily the copied binary's source. `tools/check_executable_provenance.py` checks the repaired collector against two distinct dummy executables without using the GPU.

## Full-model panels

Mode 19, both projections on four-bit activations, `--seq-sched 6`, traced. The decode panel runs 32 independent streams, 64-token prompt and one target step per stream. The prefill panels run 128 and 256 rows. All comparisons use `tools/run-batch-compare --pin-clock`; the paired runs order each width control, candidate, candidate, control. One 43-second admission bound cut off the last 128-row control and the 256-row block; 256 was taken as a separate control/candidate pair. The wrapper released the GPU lock and restored the resident service on timeout.

The 128-row pass improved almost ten milliseconds *outside* the two projections while host demand changed. Do not call that a kernel win. The 256-row step similarly saves 4.7 ms outside the projections while the projections add 2.6 ms. Decode is the target width: the candidate input projection is 20.3% slower and its slight output-stage gain does not offset it. The residuals compare the numerical map across full-model runs, including the target decode width.

The decode paired hold sampled 2428 MHz p50, 6.0 host cores busy, 5.0 other cores and package-power limiting in 45% of the window. The separate 256-row hold sampled 2648 MHz, 4.1 host cores busy and limiting in 27%. Compare arms within a hold and use the five unaffected phases as a control, not wall times between holds. Four in-process diagnostic rounds at decode width also returned the same residual for both arms. They are **not** a production comparison: changing `seq-sched` from 6 to 7 changed `gdn-resident-core` from 26.5 to 46.1 ms on the diagnostic build, and the same jump occurs on the ordinary build. That cross-phase change dominates the whole-step number and cannot be charged to this weight request.

The register premise behind the experiment was wrong at the target shape. The deployed input projection's `TT=2, WV=4` form takes 91 VGPR and permits **16** waves/SIMD, while the candidate takes 104 and permits **12**. Neither spills. The earlier round-trip report noted that 104 is below the nominal 128-VGPR twelve-wave budget, but it missed the four waves the 91-VGPR kernel already had. At prefill width the same request actually cuts `TT=4, WV=2` from 180 to 153 VGPR, moving eight to nine waves, and still does not deliver a controlled projection gain. A request has to recover enough dependency time to pay its occupancy and scheduling cost; this one does not.

The cache pin remains the ablation reference: at generation width this scheme recovers none of its 7.1% and makes the full step about 0.8% slower. A further cover experiment must establish an occupancy-preserving placement and measure the production build at 32 streams, not count the nine live operand registers against the wrong wave budget or compare a diagnostic selector against an unrelated cross-phase change.
