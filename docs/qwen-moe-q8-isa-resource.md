# Installed Qwen Q8 decode: resources are not the missing operand

The 8,192-output Q8_0 projection is the largest homogeneous nonexpert decode group: forty calls per token, 3.887 ms/token on the seven warm depth-1024 traced steps, for 713.032 MB of modeled one-read image. That is 183.5 GB/s of *logical image bytes divided by traced kernel duration* against the separately measured 242 GB/s stream reference. It is not measured physical DRAM traffic or an unprofiled wall rate. This investigation resolves a narrower question before another Q8 wave-width port: **does the selected executable spill or carry a large live operand that reducing registers would recover?** No.

I extracted the Q8 MMVQ code object from both the installed `3f552c2` HIP library and the original traced `b4c67ced9` library. They have different complete-object hashes, but the selected `mul_mat_vec_q<(ggml_type)8, 1, false, false, false, false>` hot loop has the same 26 instructions in both after removing code addresses. Both metadata entries report **17 VGPR, 25 SGPR, zero spills, zero private scratch, zero group LDS, wave32 and workgroup32**. The trace reports allocated VGPR count 24, scratch 0, LDS 0, and grid 262,144 threads / 32 = **8,192 independent one-wave workgroups**, one per output row, on each of all 320 recorded width-8192 Q8 dispatches. This is not the register-heavy two- or eight-wave configuration rejected by the earlier full-model panel. A register-only cleanup cannot remove a spill that does not exist; neither a wave split nor changing the C++ spelling of the paired ushort load solves this specific resource problem.

The installed loop is more informative than a generic Q8 arithmetic budget. Its code issues a 64-bit activation load, a 32-bit activation scale load, a 64-bit packed-weight load and a 16-bit weight scale load; the packed weight load is already a `global_load_b64`, not two scalar 32-bit transactions. Its two integer dots are `v_dot4_i32_iu8`, followed by the installed FP32 multiply and `v_fmac_f32_e32` fold. The first load is followed by eleven intervening instructions before `s_waitcnt vmcnt(2)`; the weight load by seven before `s_waitcnt vmcnt(1)` gates the first dot. `s_waitcnt vmcnt(0)` gates the second dot/scale. These waits and a one-wave row schedule make **latency cover across the next input block** a concrete alternative to more arithmetic or register shaving. They do not establish that load latency, rather than physical traffic, is the measured bottleneck: no counter-free dependency stall or physical DRAM-byte measurement was made. Changing when the next block is fetched can keep each block's two dot4s and FP32 fold in the same order, but still needs full-logit identity and whole-model rates before adoption.

Reproduce with `python3 tools/qwen-moe/q8_isa_resource.py ../../data/qwen-moe/runtime/current/bin/libggml-hip.so --trace ../../data/qwen-moe/q8-unprofiled/trace/gpu-host/1886571_kernel_trace.csv --output ../../data/qwen-moe/q8-isa-resource/receipt.json`.

This is a checked installed-ISA/resource negative in the one-row Q8 MMVQ grammar, not an ISA-independent lower bound or GPU speedup. No engine or model image changed, and no GPU lock or service was touched. **Next:** profile ordinary width-8192 calls without counters and try a bounded one-block lookahead with the same dot/fold order; inspect register count and cache/DRAM transactions before selecting it. Measure full-head plain decode and prompt/batched regressions if a candidate survives the isolated test.
