# Installed Qwen GDN: guarded in-place indexed cache update

The pinned Qwen3.6-35B-A3B on-demand runtime now avoids the complete 32-stream recurrent-state gather on its stable generated schedule. Native source `7861dc746ed49c6bec1aa2c4f4b8f25b1bf59674` is packaged and selected at `../../data/qwen-moe/runtime/current`. The installed 465-token/32-step panel reproduces the original reference's **7,946,240 FP32 logits bit-for-bit** and all greedy IDs. Four complete 32-stream generated arms reproduce **192 × 248,320 FP32 logits** each, while an independent installed-binary run reproduces their complete head bytes. At the timed generated steps 2–5, the selected source's control/default paired panel averages **147.169 → 124.023 ms per 32-token step**, or **217.44 → 258.02 aggregate tokens/s (+18.66%)**. These are full-model full-head rates, not isolated GDN timing; the second control needed a separate GPU hold after the first hold's 43-second limit, and host load ranged from 1.9 to 3.2 cores. The first control and both default processes were in one hold, and the direction agrees with the preceding four-arm candidate panel (220–221 → 257–259 tokens/s). The installed generated run measures 250.49 tokens/s under 4.2 competing host cores.

## Whole state and numerical map

The selected gathered path reads `cache[m[i]]` into temporary state, then GDN loads it and writes directly to `cache[head+i]`. The selected direct path puts `s_copy_main` on GDN's row-index input and passes a cache destination view as source slot 9 of the op. CUDA's existing GDN kernel still loads the initial state shard into registers, performs **the same FP32 recurrence in the same order**, and writes that shard to the cache rather than to the temporary. No new scatter launches. At 32 rows × 524,288 FP32 values × 30 GDN layers, deleting the temporary write/read removes **4,026,531,840 logical state bytes per generated step** in this declared graph, not a measured DRAM count or a universal traffic lower bound. An earlier same-body profiler trace records thirty large state gathers for the seed and **zero** for the two generated calls; the source and trace hashes are in the receipt.

The generated branch is guarded at graph construction by `n_seq_tokens=1`, exactly 32 sequences, `n_rs=32`, `head=0`, no zero row, and `s_copy_main[i]=i` for every row. Graph reuse additionally compares the *current* map's identity decision with the cached graph's selected decision; a changed map cannot reuse an incompatible graph topology. The graph remains default-on in this measured domain; `GGML_CUDA_GDN_FUSED_ROWS=0` restores the gathered control. All other shapes take the original gather/copy path. The kernel's input and output rows are identical for each CTA; separate CTAs own disjoint rows and each tile's initial state is loaded before its store. This is a safe row-dependency schedule in the stated domain, not a proof that every reordered batch shares it.

A diagnostic serialized the **whole 2,114,206,957-byte context after generated step 2** in both arms and compared the files byte-for-byte; SHA-256 is `03e373f28f624b26fb00d447dc7d79d74216009eadabdec77cb4fb3fe98f9427`. The matching full heads alone would not have established the state transition. A second actual two-ID swap after the stable seed splits into 31+1: the final selected guard takes the gathered path and reproduces **all 96 full heads and the entire serialized 2.114-GB state byte-for-byte**. Its profiler shows thirty `8192×512` seed gathers plus thirty `7936×512` and thirty `256×512` gathers for the two reordered subbatches. This matters because merely checking each subbatch's *local* identity map is insufficient: the earlier in-place candidate changed **all 248,320 FP32 values in the first swapped output row** and its serialized state while all other rows matched. The failed outputs and state files are retained. Graph reuse had also originally checked only `head/n_rs/zero`, not the input row values, which would have allowed a cached fused graph to cross a map change; the installed graph predicate repairs that mechanism.

The other failed arm enabled in-place writes on multi-token prompt chunks. At the same 465-token workload it changed the first full head and greedy trajectory despite an apparently identity row map. It was excluded from the installed dispatch, not relabeled as an FP32-tolerated alternative. The earlier split-read/separate-`SET_ROWS` route preserved logits but moved the 19-ms gather into ~22-ms scatter and saved no logical bytes; the selected source removes its unused non-ring split dispatch. The ring-state consumer is still available where its model requires it.

## Whole-model acceptance and limits

The packaged and installed revision both match the pinned original 465-token prompt's 32 full heads, SHA-256 `9f312017bddf33b97c5cbe4fce239e811f39cfcc1c128a7efb394566cf81a969`. A same-binary depth-1024 ordinary call comparison at 512 prompt tokens/64 decode tokens (three repetitions each) reports prompt **1099.05/1122.05 tokens/s** and single-stream **50.66/51.16 tokens/s** control/default under a power-limited, host-busy socket. Both are unchanged dispatch shapes; these samples do not establish a single-stream or prompt gain. The packaged candidate's 465-token acceptance and the installed 192-head generated replay were performed under `tools/run-batch-compare`; after every GPU hold `bonsai-halo.service` was active and the GPU lock free. The resident Bonsai service was not replaced.

[The analyzer](../tools/qwen-moe/gdn_fused_result.py) checks per-arm head hashes, state-file equality, the rejected prompt/swap contrasts, trace geometry, rates, and source/executable hashes. [Final receipt](../../data/qwen-moe/gdn-fused/domain-receipt.json) SHA-256 `59a86d2f1e02976ef45b55d27bd4f0707bf2095059b3101927cbb9113c2f2dc5`, [selection acceptance](../../data/qwen-moe/gdn-fused/domain-acceptance.json), all stdout/stderr, profiler CSVs, complete heads and state files stay under `data/qwen-moe/gdn-fused/`. The installed `runtime-source.git` branch `build-7861dc746...` and package source bundle own the native implementation. Hardware time is measured only for this 32-stream shape at short occupied positions; longer context and dynamic served client order require separate panels. An independent next question is whether a direct indexed writer can be valid on reordered and one-stream calls *without* changing the required state observation. Until then, their gathered fallback is part of the selected contract.
