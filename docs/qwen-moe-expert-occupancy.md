# Qwen expert tile occupancy on actual prompt routes

The next routed Q4/Q5 consumer should measure *small expert groups*, not assume that a 126-row prompt gives each expert a large GEMM. The selected model has 256 experts and eight assignments per row. We counted all forty layer routes from the disjoint 113-token train and 126-token held prompt captures. These are the callback-cut routes documented in [all-layer routes](qwen-moe-all-layer-routes.md), not generated decode routes.

The native `mul_mat_id` dispatch in the pinned Prism source chooses MMVQ for at most eight **total token rows**, then MMQ for larger quantized expert banks. It does not choose MMVQ independently for each small expert group. `ggml_cuda_mul_mat_q` groups assignments by expert and supplies `expert_bounds`. On gfx1151, the Q4_K/Q5_K MMQ configuration offers column tile widths 16, 32, 48, ... 128. `mul_mat_q_switch_J` selects a width using `args.ncols_max`, which `ggml_cuda_mul_mat_q` sets to the **full input token count** `ne12`, not the occupied column count of any expert. The kernel tests the group's bounds and skips empty groups. It does not necessarily execute all the masked column arithmetic; the slot counts below are capacity, not device instructions or bytes.

| Prompt split and window | Assignment groups | Singletons among groups | Assignments in groups of at most 4 | Largest group | Globally selected J | Filled slots at fixed J | Filled slots with one smallest 16-multiple tile per group |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Train, 32 rows | 10,685 | 36.9% | 44.9% | 32 | 32 | 10.58% | 20.77% |
| Held, 32 rows | 11,260 | 37.6% | 40.8% | 32 | 32 | 11.19% | 21.87% |
| Train, whole 113 rows | 4,888 | 23.7% | 14.1% | 104 | 128 | 5.78% | 40.33% |
| Held, whole 126 rows | 4,958 | 23.2% | 12.9% | 123 | 128 | 6.35% | 42.45% |

At held width 32, 40,320 assignments occupy 360,320 fixed-J slots. Picking J=16/32 per expert would use 184,384 slots with **the same 11,260 nonempty expert tiles**, a 48.8% reduction in unused column capacity without duplicating any complete expert-image read in this grammar. For held whole-prompt grouping the capacity falls from 634,624 to 94,992 slots, an 85.0% reduction with the same 4,958 expert tiles. Blindly forcing J=16 is different: it needs 11,524 tiles at width 32, or 5,937 instead of 4,958 on the whole prompt. Re-reading weights for those extra tiles can erase any instruction benefit. Empty-expert dispatch, launch geometry, quantizer scattering, weight reuse and output ordering still count.

This is an exact finite-workload **occupancy and capacity** result, not a native speedup or a claim that masked lanes consume the full tile's work. The full-row dispatch and group-bound checks explain why a smaller per-expert tile is a meaningful native experiment despite already grouped assignments. The next experiment should instrument active group size against issued instructions and per-expert MMQ time on the selected binary, then compare a one-image-per-group adaptive width with its fixed-J predecessor under a matched whole-model prompt and batched generation panel. A single-token decode still uses MMVQ, so a prompt-only improvement must not be presented as single-stream decode gain. Preserve each row's dot-product fold and selected logits for any exact scheduling arm.

`tools/qwen-moe/expert_occupancy.py` checks every captured input hash against the original receipt and writes the full group-size histograms, counts and source hash to [the CPU receipt](../../data/qwen-moe/all-layer-routes/occupancy.json). No GPU reservation, executable, model image or resident service changed. Native source reference is Prism `1a07bfa5f`; `ggml-cuda.cu` dispatch, `mmq.cu` argument and selection, `mmq.cuh` group bounds, and `mmq-config-rdna3-5.cuh` Q4_K/Q5_K tile configurations have SHA-256 values `ea2358d8`, `af008202`, `71886535` and `19f0fe86` respectively (prefixes). The selected on-demand runtime differs from this source only in the GDN precompute described in [speedup integration](qwen-moe-speedups.md).
