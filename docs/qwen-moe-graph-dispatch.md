# The Qwen router runs two different CUDA programs

The selected runtime's [counter-free trace](../../data/qwen-moe/q8-unprofiled/receipt.json) has an unusually clean dispatch distinction. Its two synthetic-depth setup evaluations dispatch 160 separate `soft_max_f32<true,256,256,float>` kernels and 160 `k_argsort_f32_i32` kernels. The eight measured single-token evaluations dispatch 320 `topk_moe_cuda<256,false>` kernels, exactly forty per token, and none of those separate softmax/argsort kernels. This is not an inference from model parameter counts. The raw trace is `q8-unprofiled/trace/gpu-host/1886571_kernel_trace.csv`, SHA-256 `25dc3dc7f77275e0f8f07bf7947636b06e8d5b09f9885a1aafa1a1f8e4710247`, dispatch IDs 0–9066 for setup and 9067–21586 for decode. Its source revision is `b4c67ced9f6bac6b1661b25714946d999374e06f`; the receipt pins the binaries and the GGUF.

| Trace region | Separate 256-way softmax | Separate argsort | Fused 256-way top-k | Device duration per relevant dispatch |
| --- | ---: | ---: | ---: | ---: |
| Two setup evaluations | 160 | 160 | 0 | softmax 4.311 µs, argsort 17.430 µs |
| Eight single-token evaluations | 0 | 0 | 320 | fused 7.418 µs |

The durations are for different shapes and cannot be subtracted as a speedup. Other router kernels, including normalization and gathering, are excluded from this table.

The source explains why the earlier [no-read probability cut](qwen-moe-batch-boundary.md) matters. Qwen35MoE calls `build_moe_ffn` with softmax gating in `src/models/qwen35moe.cpp`. `src/llama-graph.cpp` builds `SOFT_MAX → RESHAPE → ARGSORT → VIEW → GET_ROWS`, followed by optional weight normalization. In `ggml/src/ggml-cuda/ggml-cuda.cu`, `ggml_cuda_topk_moe_fusion` recognizes that sequence, and `ggml_cuda_compute_forward` replaces the whole sequence with `ggml_cuda_op_topk_moe` when its subgraph and memory predicates pass. The CUDA implementation in `topk-moe.cu` computes its own warp-local softmax and repeated top-k reduction. It is not required to have the same FP32 reduction order, exponential rounding or normalization as the separate softmax/argsort/get-rows program. The graph callback's view ends **at** `ffn_moe_probs`, the softmax node. That view cannot match a fusion pattern requiring the subsequent reshape and argsort. A view ending at router logits does not interrupt that pattern.

This identifies a useful intervention without a rebuild. `GGML_CUDA_DISABLE_FUSION=1` is already read by `ggml_cuda_compute_forward`. Under the same selected binary and pinned GGUF, **without any callback**, all 39 full-vocabulary comparisons across widths 1, 2, 4 and 8 and offsets 0–3 have zero differing bits. This includes the first continuation row that differed in 248,319 floats under the ordinary no-cut map. An independent no-cut callback arm with fusion disabled also gives zero differences on that row. Both bounded panels used `tools/run-batch-compare --runtime-max 42s --memory-gib 30 --host-reserve-gib 4 --exec`, four generated tokens, context 2048, batch 512, ubatch 256 and flash attention; the wrapper restored the resident service. [Raw logs and source/binary/model/input-hashed receipt](../../data/qwen-moe/acceptance/batch-layer-probe/fusion-dispatch-receipt.json) stay beside the previous controls. This is a measured **exact width-invariant map for these 39 rows**, not a sampled-quality or rate claim.

The ordinary singleton uses a fused router in the trace; the probability cut destroys the source pattern needed to fuse it; global fusion disable equalizes widths without a graph cut. Together these make MoE top-k fusion the first concrete candidate for the numerical fork, rather than grouped expert dispatch.

## Top-k-only intervention

A source branch from the selected runtime, `2573923a`, adds `GGML_CUDA_DISABLE_TOPK_MOE_FUSION=1` at the top-k pattern alone. All other fusion decisions stay enabled. With no graph callback, **all 40 compared full-vocabulary rows across widths 1, 2, 4 and 8 reproduce singleton logits bit for bit**, or 9,932,800 compared floats and zero bit differences. The ordinary selected path had 248,319 differing floats on the first two-token continuation row; the global-disable control also had zero. Thus disabling the MoE top-k fusion is sufficient for this width-invariant map. The full stdout/stderr, diagnostic and HIP binary hashes, pinned model and source revision are in [the targeted receipt](../../data/qwen-moe/acceptance/batch-layer-probe/targeted-receipt.json). The branch is in `data/qwen-moe/runtime-source.git` under `research-targeted-topk-2573923a`. The selected runtime and serving map did not change.

This does not prove that its softmax reduction alone causes the difference; fused selection, normalization and graph scheduling all change together. It does establish a narrower intervention than globally disabling every CUDA fusion. The first report missed two complete JSONL records produced after the attended command timed out. The two arms ran sequentially in one GPU-wrapper reservation on the same `2573923a` binary, depth 1024, 64 decode tokens and three repetitions. Fused top-k averaged **52.1825 tokens/s** (51.8217, 52.2937, 52.4321); disabling only that fusion averaged **49.3624 tokens/s** (47.2575, 50.4418, 50.3879). The unfused arm takes 5.81% more time on all three samples and 3.86% more on the last two. This is a complete-model single-stream decode loss on the recorded shape, not a kernel ratio. The 55-second attended timeout occurred while the bounded wrapper still ran; its log has no terminal restoration record. A later service check found Bonsai active and the GPU lock free. Neither clocks nor host load were captured, and the arms were not alternated, so do not infer an exact stable 5.81% cost. [The recovery receipt](../../data/qwen-moe/acceptance/batch-layer-probe/speed-recovery.json) hashes both raw samples and gives the original command and thread entry. The previous [targeted receipt](../../data/qwen-moe/acceptance/batch-layer-probe/targeted-receipt.json) remains as evidence of the incorrect no-sample conclusion.

This intervention fixes the observed width mismatch but pays for it at the measured decode shape. It is not selected. The next useful experiment is to preserve the fused dispatch while making its singleton and multi-row arithmetic agree, or to prove an output contract that makes the difference harmless. Compare router IDs and normalized scores without a graph-cut observer effect, then replay the MTP token-71 fork. Any replacement needs prompt and batched throughput as well as exact greedy acceptance before a default change.

[The no-cut selected-graph allocation study](qwen-moe-mtp-near-tie.md) explains why merely forcing this fast fused kernel onto two causal rows is invalid: normalized row-0 weights alias the second row's 1,024-byte router logits in the same device buffer. One warp writes the 32-byte output while another may still read that input. The one-row exception in the native fusion guard is a necessary memory-lifetime constraint for this allocation, not merely an untested shape heuristic. A nonoverlapping output address is the concrete next lowering before exact-width and MTP acceptance can be retried; no selected runtime changed.

The first targeted replay exposed a GPU wrapper race: it released the exclusive lock before recreating the transient resident service, and another panel could mask the unit between its unmask and `systemd-run`. The wrapper now restores while still holding the lock; a clean 40-row replay with the repaired wrapper ended with the service active. Starting the service once per panel in a queued series costs startup work, but prevents the last panel from inheriting an unpaid restoration debt. This is a service-lifecycle repair, not a Qwen throughput result.
