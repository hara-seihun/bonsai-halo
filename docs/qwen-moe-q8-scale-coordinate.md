# Exact modal Q8 scale codes do not improve the installed image

The [paid per-input-block FP16 dictionary](qwen-moe-q8-scale-sharing.md) stores 58,793,258 scale-sidecar bytes for all 250 nonembedding, nonexpert Q8_0 tensors. Its fixed-width output-row index looks wasteful when a scale dominates one input-block column. This census asks whether a two-level direct code can exploit that skew *without changing a single Q8_0 code byte or FP16 scale bit*.

For each K-block column with `R` output rows and `D` distinct FP16 scale words, the existing format pays `2D + ceil(R ceil(log2 D)/8)` bytes plus an 8-byte directory. The candidate places the most frequent word at index zero, pays the same `2D` dictionary bytes, a `ceil(R/8)`-byte exception bitmap and `ceil((R-f) ceil(log2(D-1))/8)` bytes of packed exception indexes, where `f` is its observed frequency. To decode an arbitrary row independently, it also pays `2 ceil(R/32)` bytes for a 16-bit exception prefix per 32 rows. A bitmap bit and one popcount within its 32-row group identify the exception rank. Its 8-byte column directory can use the high bit of its dictionary length as an arm selector. Every input-block column can independently retain the existing format if the candidate loses. The prefix counter fits: the largest tensor has fewer than 65,536 rows. This is a **storage and lookup-work comparison**, not a claim that a native extra bitmap/rank lookup is fast.

[The source and complete 250-tensor, 16,640-column, 43,909,120-block census](../../data/qwen-moe/q8-scale-coordinate/receipt.json) tie each tensor's payload SHA-256 to the pinned GGUF header, acquisition receipt, inventory and script hash. **Zero columns prefer the paid modal code.** Even if all prefix ranks are free, only 37 columns prefer it and the whole bank saves **971 bytes**. The best paid column loses 21 bytes relative to the fixed index; the most common word in any column occurs 206 times, while the largest modal *fraction* is only 3.516% (a different column). The direct per-K bitmap/exception coordinate therefore cannot improve the existing 58,793,258-byte image, even before its decode instructions or extra memory requests. The 1.10521% conditional whole-model scale-byte saving already found remains the candidate worth considering; there is no new image to install.

This is a bounded negative for **one per-K exact dictionary with a modal bitmap and fixed-width nonmodal indexes, independently addressable output rows, and paid rank checkpoints**. It is not a bound on cross-K correlation, adaptive entropy coding, changed Q8 representations, or composed producer-consumer maps. The observed empirical per-K Shannon quantity plus original dictionary literals and 8-byte directories would be 52,394,633 bytes, 6,398,625 below the existing sidecar, but that is *not* a lossless-image lower bound: frequency metadata, random-access checkpoints and coding machinery are omitted. Even achieving all of that optimistic gap would save just another 0.244% of the modeled complete one-read stream, before inference costs. The better independent question is native generated-phase GDN state traffic (held by its owner) or calibrated physical Q8 transactions/waits, rather than another per-K scale shortcut. No GPU, executable or resident service changed.

Reproduce the CPU census from the registered source checkout or canonical master after publication:

```sh
python3 tools/qwen-moe/q8_scale_coordinate.py --count 250
```

Per-tensor JSON and the aggregate receipt live in `../../data/qwen-moe/q8-scale-coordinate/`; the script checks the existing paid-sidecar receipt's exact fixed-width byte count before publishing its own aggregate.
