# Qwen routed-score pushdown nearly preserves down input codes, but not the native map

The real identity `sum_e a_e (W_e h_e) = sum_e W_e (a_e h_e)` suggests moving eight positive normalized router scores into the 512-wide post-SwiGLU inputs, potentially fusing the expert sum with down projection. This is **not** an arithmetic identity for the installed mixed Q5_K/Q6_K packed consumer: its prompt MMQ quantizes each `h_e` to Q8_1 before the integer dot, then applies decoded scales, affine sums and ordered FP32 output folds. The selected grouped dispatcher already groups experts and quantizes their distinct down inputs. Its one-row MMVQ and prompt MMQ are different consumers.

[The CPU capture census](../../data/qwen-moe/score-pushdown/receipt.json) applies the reciprocal `d_inv=127/max(abs(x))`, `roundf(x*d_inv)`, `d=1/d_inv` rule from the pinned native `quantize_mmq_q8_1` to **both** actual disjoint 64-token post-SwiGLU producer/score captures at all forty layers. It separately forms FP32 `a*x` before quantization, versus keeping the original integer codes and multiplying their **already FP16-rounded** scale and sum by `a`. An extra *free oracle* uses unrounded FP32 metadata before multiplying by `a` to isolate double rounding. Q5_K's DS4 input stores FP16 `d` and the FP16 rounded sum of 32 values. Its eight four-float thread sums reduce with XOR offsets 4, 2, 1; the CPU reproducer uses that order and CUDA's ties-away `roundf` convention. All scores are positive and every 32-float block is finite and nonzero. The native fused SwiGLU producer and GPU round instructions are not replayed bitwise by this CPU calculation.

Each code change is one integer level, so the *integer-code coordinate* is nearly score-equivariant on this capture. The selected FP16 scale/sum coordinate is not: about a quarter of held blocks differ from score-first quantization because the selected input has already rounded its metadata before the score can multiply it. FP32 scale values differ in **152,657 train / 152,551 held** blocks. Granting free unrounded metadata produces the much smaller oracle numbers above, but this is **not the installed input format**. Thus actual score pushdown changes many down-dot operands before any output summation even in this CPU grammar. A GPU kernel that reused the old codes but scaled metadata could not claim to reproduce a graph that explicitly requantized `a*h`; conversely, moving the score ahead of the already selected quantizer changes the selected graph's dot/fold ordering even if all input words matched. Multiplying the FP16 sum after input preparation rather than recomputing it from FP32 score-scaled values also fails frequently. No complete logits, language loss, native speed or original-BF16 image was changed or measured.

**Cost boundary.** Score pushdown does not remove any of the eight weight-image reads or integer dots. Even a free fused consumer which eliminated *both* a write and read of all eight FP32 2,048-wide expert outputs at every layer could avoid at most `2*40*8*2048*4 = 5,242,880` logical bytes/token, **0.1996%** of the conditional 2,626,187,904-byte whole-model one-read weight stream. This is an optimistic logical-byte comparison, not physical DRAM or wall-time bound; output epilogue dispatch/temporary lifetime could still matter independently. Exact output arithmetic should keep score application at the reference output boundary and measure a fused *post-dot* epilogue with finite-head/state acceptance rather than rely on the real-algebra pushdown. An approximate score-first image would require held complete-model loss and whole-model native timing, not this local near-equality.
