# The exposed gfx1151 `GL2C_MC_RDREQ` is not a calibrated DRAM-byte counter

**Question.** After the [counter-free Q8 event panel](qwen-moe-q8-event-panel.md) removed the profiler-shaped slow-layer episodes, can the profiler's `GL2C_MC_RDREQ_sum` distinguish physical off-cache traffic from repeated packed Q8 loads? Its name suggests memory-controller requests; the previous [GL2C read calibration](qwen-moe-gl2c-calibration.md) had established only that `GL2C_EA_RDREQ_*` reports half a known stream.

**Measured negative.** On the same gfx1151 GPU and ROCm 7.2.3, a known kernel explicitly reads every word of a 16, 64, 128 or 256 MiB initialized input once. `GL2C_MC_RDREQ_sum × 128 / bytes read` is **0.50003, 0.50004, 0.50004, 0.50002** in the four cold-size arms, matching `GL2C_EA_RDREQ_128B_sum` almost exactly. The new replay reads the **same 16-MiB prefix three times**, then the same 256-MiB region twice, then the 16-MiB prefix again. The first three durations are **177.3, 45.9 and 33.6 µs** under the instrument, while the purported memory-controller requests stay **65,540, 65,541 and 65,537**. The 256-MiB arms take 1,361 and 1,303 µs, with **1,048,688 and 1,048,577** reported requests; the final small arm takes 82.3 µs and reports 65,537. Cache residency is a plausible explanation of the timing contrast but not directly measured here. The decisive property is that the requested metric is just as insensitive to repeated reads of the same cache-sized region as the previously disqualified EA metric and reports only half even for 256 MiB. Its units and attribution cannot be interpreted as physical bytes by multiplying by 128 (nor corrected by simply doubling).

A targeted selected-binary Qwen run collected both counters on all **582/582 positive quantized calls** in a two-token, complete-head `llama-bench -n 2 -p 0 -d 0` profile. The eighty ordinary wide-Q8 calls (40 per token, grid 262,144) report medians **69,666 EA and 69,671.5 MC requests**, with pooled MC/EA **1.0001012**; the other selected quantized families are likewise close to one. This is a join to the actual ordinary consumer, not a Qwen physical-transaction measurement or a graph-on timing sample. Profiling changes scheduling, the no-warmup two-token panel does not establish whole-model speed, and no Qwen numerical map or selected runtime changed. The [event panel](qwen-moe-q8-event-panel.md) owns the matched complete-head numerical control and wall perturbation of the unprofiled markers; this counter experiment makes no speedup claim.

**Consequence.** Do not derive DRAM-byte bandwidth, repeated Q8 image traversals, or a 2× Q8 traffic remedy from either exposed GL2C counter. The available `rocprofv3 --list-avail` on this host names no independently calibrated physical DRAM-byte metric; `GL2C_HIT/MISS` also remain nearly fixed across the three short replay reads. An independent next engine experiment should alter the ordinary Q8 kernel's memory-level parallelism or output-row scheduling in a *matched graph-on full-head wall panel*, with no assumed DRAM explanation; alternatively first locate and validate an actual memory-controller byte source against both the repeated cache-sized and streaming controls before applying it to Qwen. A reduction in ISA issue slots or in these counters alone is not that experiment.
