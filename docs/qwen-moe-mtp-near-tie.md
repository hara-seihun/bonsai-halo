# Why simply forcing fused router top-k at MTP width is unsafe

The selected Qwen3.6-35B-A3B runtime runs fused MoE top-k at a one-token decode width, but executes the unfused softmax/argsort/normalization at multiple causal tokens. That dispatch difference changes almost every vocabulary logit on the established two-token replay; a four-token alignment also reverses the same near-tie choice at generated index 71 that separates plain greedy from Q4 MTP. [The graph-dispatch diagnosis](qwen-moe-graph-dispatch.md) showed that disabling only this fusion makes forty full-vocabulary width comparisons bit-identical but costs complete-model decode time. This experiment asks whether the fast fused path can simply be enabled for multirow verification.

## No-cut allocation observation

A diagnostic callback returns `false` at every graph node: it only records the graph tensor's allocated address during the backend's pre-execution visit and never requests a graph cut, tensor copy or synchronization. The selected `3f552c2` binary computes the same control as before: on the list prompt's first two-token continuation, width two differs from the width-one logit row in **248,319/248,320 FP32 bits**, with maximum absolute difference **0.197882652** and unchanged argmax ID 248068. The raw wrapper log retains the graph allocation observations and service restoration; [the normalized, source/binary/model-hashed receipt](../../data/qwen-moe/acceptance/router-alias/receipt.json) rebases pointers per evaluation.

| Layer-0 graph tensor | Singleton offset / bytes | Two-row offset / bytes |
| --- | ---: | ---: |
| Router logits, 256 FP32 per row | 0 / 1,024 | 0 / 2,048 |
| Softmax output | 0 / 1,024 | 0 / 2,048 |
| Argsort IDs | 262,144 / 1,024 | 262,144 / 2,048 |
| Unnormalized selected weights | 524,288 / 32 | 524,288 / 64 |
| **Normalized selected weights** | **1,024 / 32** | **1,024 / 64** |

These are relative addresses in the same allocated device buffer within each evaluation, not assumed equal absolute addresses across evaluations. In the multirow graph, normalized row-0 output occupies **[1,024, 1,056)**, overlapping router *input* logits of row 1 **[1,024, 2,048)**. No such overlap exists in the singleton graph: its logits end at 1,024. Other layers can have different placements; this one layer suffices to reject unconditional multirow fusion for the selected graph.

The selected source's `topk_moe_cuda<256,false>` assigns one row to a warp, four warps per CTA. It reads its own eight 32-lane logit fragments and later writes eight selected FP32 weights. A row-0 warp can reach the normalized output store before the row-1 warp has loaded all of its input. Warps in the CTA have no read-before-write barrier. Even one CTA therefore has a write/read race at these addresses; no kernel launch ordering can repair it *within* that launch. This proves **the candidate program formed by removing the multirow fusion guard is not a valid exact lowering** on the observed graph. It does not assert that a corruption occurred: the guard presently declines the fusion, and neither a kernel race nor a changed result was deliberately run.

`ggml_cuda_check_fusion_memory_ranges` has a special one-row top-k exception and otherwise checks whether fused outputs overlap external source inputs. The two-row collision explains the shape predicate as a real memory-lifetime constraint, not merely an arbitrary width policy. The existing unfused graph may legally reuse the region because separate kernels enforce read-before-write order. At least the 64 output bytes for two normalized rows must instead have a live address disjoint from *both* input logit rows to enable a single-launch fused two-row consumer; this is an address constraint, **not** a claim of 64 extra allocated bytes or a bandwidth speedup. An allocator could reuse some other dead region. A fused program with a separate temporary and an ordered copy would also pay for that copy and its launch unless a downstream address is changed. Avoid a warp barrier as a supposed repair: it cannot synchronize distinct CTAs at larger verification widths, and a block barrier after the load needs every row's complete input retained and still must establish its cost and numerical map.

This sharpens the next engine question. Arrange **nonoverlapping normalized-weight storage** at multirow graph construction, then let the existing fusion predicate decide, comparing the unchanged full target at widths 1/2/4/8, the token-71 MTP fork and complete decode/prompt/batched throughput. Merely deleting the predicate is not an acceptable experiment. The top-k-only disable result is a numerical control, not a throughput proposal. Q4 MTP remains opt-in; no runtime, image or serving default changed in this study.
