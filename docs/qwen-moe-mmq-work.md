# Qwen expert MMQ work after group-bound masking

The prompt expert kernel really does compute padded columns. In the pinned Prism `mul_mat_q`, a block returns when its expert group has no tile at that `J` index, but a nonempty block stages all `J` activation columns and calls `vec_dot` for the full `I × J` output tile. `tile_y_max_j` reaches only `write_back`. The Q4_K/Q5_K matrix body loops over `J` in 16-column MMA tiles without testing the expert's remaining columns. This resolves the ambiguity in [the group occupancy study](qwen-moe-expert-occupancy.md): its unused slots correspond to executed matrix-tile positions for active blocks, not merely allocated output storage. It does not imply that wall time scales with those positions.

For the disjoint held 126-token actual-route capture across forty layers, the source selects J=128 for the whole prompt. Of 4,958 active expert groups, 4,909 contain at most 64 assignments. A uniform **J=64** would execute 50.5% of its current full-tile output positions, at 5,007 instead of 4,958 logical passes over the expert image, a 0.99% increase. Both J=64 and J=128 use I=128 rows and 256 threads on gfx1151. At 32-row tiles, the selected J=32 and an alternative J=16 both use I=64 and 128 threads; on held routes J=16 executes 51.2% of full-tile output positions and makes 11,524 rather than 11,260 expert-image passes, 2.34% more. The train capture agrees: 50.2% positions and 0.39% extra image passes for J=64 versus J=128 at whole width; 50.9% positions and 1.85% extra image passes for J=16 versus J=32 at 32 rows.

The down projection has twice as many output rows, so its position counts double and its ratios are the same. Q4 gate/up and Q5 down execute a fixed K loop for each surviving tile. The position count is `sum_groups ceil(group_size/J) × ceil(output_rows/I) × I × J`; the logical complete-image pass count is `sum_groups ceil(group_size/J)`. This is a static issued-tile accounting for the non-stream-K RDNA4 specialization, not DRAM bytes, exact ISA instruction totals, or a GPU-time bound. Some bytes can come from cache. Smaller J changes occupancy, barriers, input staging and scheduling; the extra image passes may cost more than the saved MMA positions. For J=32 on a whole prompt, I falls from 128 to 64, an especially poor assumption for a weight-bound kernel even though the arithmetic-position ratio is .263. MMVQ handles eight or fewer total token rows and is outside the calculation. Single-stream decode has no gain from this intervention.

This points to a short native experiment instead of an adaptive per-expert dispatcher. Force the already compiled J=64 arm on a whole-prompt MMQ shape and J=16 on a 32-row prompt shape, one at a time, with the original packed image and reduction order. Compare expert phase *and* full-model prompt time with clock records, plus batched generation for regression. Check finite logit bits before accepting either schedule. If a smaller J wins, only then pay for mixed widths inside one launch. A per-expert adaptive rule is not free: separate launches per expert would throw away the grouping advantage, and a mixed-template kernel must reconcile differing row tiles and grid geometry.
