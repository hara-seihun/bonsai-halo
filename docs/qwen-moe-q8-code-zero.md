# Rounded Q8 gate/up input zeros do not form skippable native blocks

The native MMQ Q8_1 preparation rounds each 32-float post-attention producer block with `d_inv = 127 / max(abs(x))` and `roundf(x*d_inv)`. On both disjoint 64-token actual selected-Qwen-GGUF prompt captures, across **all forty routed layers**, integer rounding produces zeros even though [none of the original FP32 inputs is zero](qwen-moe-gateup-zero.md). This study asks whether those new zero codes can avoid the selected eight routed experts' Q4_K gate/up consumption. Each token has one shared 2,048-wide prepared input for those eight experts.

| Per split, 40 layers × 64 tokens | Train | Held |
| --- | ---: | ---: |
| Zero Q8_1 individual codes / 5,242,880 | 56,186 | 55,090 |
| Zero contiguous two-code groups / 2,621,440 | 627 | 599 |
| Zero contiguous four-code groups / 1,310,720 | 53 | **52** |
| Zero contiguous eight-/sixteen-/thirty-two-code groups | **0** | **0** |
| Four-code groups after first token (40 × 63 × 512) | 1 | **0** |

All 52 held four-code groups occur in the **first token**: 1 each in layers 10–11, 2 each in layers 12–14, 3 each in layers 15–25, 2 each in layers 26–29, and 3 in layer 30. The train split has the same 52 first-token groups plus one at layer 0/token 18. These are positions in *one shared activation*, not separate skips for each expert; the free image-byte accounting multiplies each opportunity by the eight selected expert banks. At native Q8_1 block granularity there is not one zero block to skip. No Q4_K weight decoder or MMQ dispatch changed.

A deliberately optimistic **independently addressable** four-input-coordinate Q4_K reader, with a free activation mask, would avoid 52 × 4 × 8 experts × 2 banks × 512 output weights × 4.5/8 bytes = **958,464 bytes across the 64 held tokens**, or **14,976 bytes/token / 0.0005703%** of the complete-model 2,626,187,904-byte/token one-read comparator. These code bits are actually in 256-input Q4_K superblocks with shared scales, not independently fetched four-element slices; this is a *ceiling* in that more permissive grammar, not a valid saved runtime program. Even a hypothetical one-coordinate reader with free indexing has just **3,966,480 bytes/token / 0.15104%** ideal gate/up image traffic to remove on held, before scale bytes and execution costs. It would need fine-grained sparse work throughout almost every 32-code block; that figure is not added to the four-code ceiling. A real reader must pay dynamic masks, scattered weight addressing, scales and synchronization. Nor does integer-code zero establish finite FP32 logit-bit identity under a changed accumulation order. This is a structural/traffic negative, **not** measured native latency, complete-model TPS or a representation-quality change.

The CPU [reproducer](../tools/qwen-moe/q8_code_zero.py) reads every post-attention FP32 producer row from the [all-layer native callback capture](qwen-moe-all-producers.md), checks its SHA-256 against the independent all-down capture receipt, and applies the reciprocal MMQ quantizer (not the scalar `x/d` Q8 variant). The [data receipt](../../data/qwen-moe/q8-code-zero/receipt.json) retains source, native quantizer, installed runtime, model, traffic and all 80 input hashes plus per-layer and split counts. The domain is these real prompt producer rows; generated tokens, a learned sparse coordinate and original BF16 weights are separate questions. The contemporaneous [down-input Q8 study](qwen-moe-rounded-down-zero.md) addresses *post-SwiGLU* inputs and cannot be added to this bound without a common reader and complete byte accounting.

**Decision:** Do not implement native Q8_1 all-zero-block or four-code mask skipping for gate/up on these prompts. The next engine experiment is the ordinary unprofiled Q8 and routed expert physical phase/transaction diagnosis; new MoE representations need changed learned directions and a paid complete image with held complete-model quality.
