# Qwen one-row Q8 next-K register lookahead: compiled schedule rejects the proposed latency cover

The installed Q8 width-8192 decode group costs 3.887 ms/token on the earlier seven-step trace, with one wave per output row and a 17-VGPR, spill-free body. Its first and second packed dots wait on independent weight/activation loads. I tried one-iteration register lookahead in the *actual* native `mul_mat_vec_q<(ggml_type)8, 1, false, false, false, false>` template: each lane reads its next eight-code Q8_0 weight fragment, Q8_1 activation fragment and scales before calculating its present block's two integer dots and FP32 fold. It keeps the same K ownership and per-lane dot/fold sequence in C++ source. The [candidate patch](../../data/qwen-moe/q8-next-k/candidate.patch) is deliberately not in the selected runtime.

The gfx1151 compiler **does not emit the intended overlap**. The [compiled ISA receipt](../../data/qwen-moe/q8-next-k/receipt.json), SHA-256 `d47f6b4b263d82c23f1f27c6d06d9cde7317782432ce01a032c4edb271839753`, pins the source patch (`e07a10de…`), compiled object (`868157d6…`), full extracted ISA and baseline object. In the steady loop, both `v_dot4_i32_iu8` execute before `v_dual_fmac_f32` at code address `…C174`; the following iteration's weight `global_load_b64` does not issue until `…C1F0`, and the loop branches back at `…C210`. A second packed 64-bit load for its activation follows at `…C1F8`. Thus **current fold → next weight load → back branch → next dot**, not next load → current dot/fold. The first load in the function is prologue and is not evidence of a steady-state pipeline. The compiler also raises VGPR 17→20 and SGPR 25→30; both versions report zero spill and scratch. These resource counts do not by themselves prove a slowdown, but the proposed next-K cover is absent. The `q8_isa_resource.py` extractor now retains the complete compiled body when a changed loop has no predecessor's `s_cbranch_execnz`, rather than failing to inspect it.

This is a checked **compiled-schedule negative** for the ordinary nonvolatile C++ register-preload expression on this kernel and compiler, not a GPU timing, a full-model speed comparison, or bit-identical runtime acceptance. The exploratory build produced `libggml-hip.so`; it was not installed or selected, and no resident service/GPU reservation changed. In particular, a C++ source expression before the dots does not guarantee early ISA loads. Next test an explicitly early-issued load schedule (and its outstanding-request count, VGPR and physical traffic) on the same one-row Q8 kernel. Only after its compiled loop actually overlaps the dot/fold should it enter a matched full-head plain-decode panel; include prompt and 32-stream regression shapes. Do not count this uninstalled candidate as a speedup.

Reproduce the CPU extraction with the native patch applied to the pinned Prism source and a gfx1151 HIP build, then run `tools/qwen-moe/q8_isa_resource.py LIB --output ISA` and `tools/qwen-moe/q8_next_k.py ISA ../../data/qwen-moe/q8-isa-resource/receipt.json NATIVE/ggml/src/ggml-cuda/mmvq.cu ../../data/qwen-moe/q8-next-k/candidate.patch --output RECEIPT`. The unmodified baseline library and original trace are linked from [the resource census](qwen-moe-q8-isa-resource.md). The receipt records SHA-256 identities and the complete candidate/selected symbol metadata; this comparison does not depend on a speculative arithmetic roof.
